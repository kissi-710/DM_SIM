# AIの速度と強さの改善計画

モンテカルロ探索(L2)の「速度」と「精度(強さ)」への不満から、設計を変えない範囲で進める改善を3項目に整理する。
進捗は [ROADMAP.md](../ROADMAP.md) の M7-15〜M7-17 が正。

## 0. 現状(計測: 2026-10)

条件: maruru / zardy の4組(同デッキ2組・異デッキ2組)、各200試合、先攻後攻は交互、モンテカルロ(A) vs ルールベース(B)。

| 設定 | Aの勝ち | 探索時間(目安) |
|---|---|---|
| ペア比較の前(反復120) | 642/800(80.3%) | 約50秒 |
| ペア比較の後(反復120、`32bee2a`) | 642/800 | 約26秒 |
| ペア比較の後(反復240) | 656/800(82.0%) | 約36秒 |

- ホライズン(先読みターン数)と事前の上乗せ(L1 の手への加点)の掃引(各600試合、反復120): ホライズン 1/2/3/4 で 72.8% / 71.2% / **82.3%** / 77.7%。上乗せ 0 / 0.08 / 0.15 で **16.0%** / **82.3%** / 73.2%。
- **上乗せを 0 にすると 16% に落ちる**。探索単体の判断は、ルールベースの手の選び方より弱い。強さの大半は「L1 の手を基準に、探索が上書きする」構造から来ている。
- 反復を倍にしても +1.75pt(誤差の範囲)。計算量を増やすだけでは頭打ちで、**手の評価の質**が効く。
- プロファイル(1試合分): プレイアウト 91%、`step` 57%(`drive` 43%、`cloneState` 9%)、`legalActions` 29%(`planPlay` 23%、`planPayment` 11%、`charsOf` 11%)。単独で10%を超える関数は `charsOf` のみ。

## 1. MCTS の並列化(M7-15)

### 目的
CPU の思考時間(待ち時間)を、使えるコア数に近い倍率で縮める。または、同じ時間でプレイアウトを増やす。

### 方針
- ペア比較にしたことで、「ラウンド(世界1つ + 全候補手の評価)」が互いに独立になった。複数の Worker に別々の世界(シード)を割り当て、各手の報酬の合計・二乗和・手同士の積和を足し合わせれば統合できる(`sum` / `sq` / `cross`)。
- 探索の本体を「ラウンドの集計」と「判定・選択」に分ける。`search` の入力は(世界の種 `seed` の列)で、出力は集計(`sum` `sq` `cross` `rounds` `errors`)。
- 再現性: 反復回数指定では、`seed` の割り当てと統合の順序を固定し、並列数によらず同じ結果にする(`sim/jobs.ts` と同じ考え方)。
- 時間指定(ms)では、再現性は求めない(従来どおり)。

### 受け入れ条件
- 並列数 1 と N で、反復回数指定の結果(選ぶ手・集計)が一致する(テスト)。
- 4 Worker で、同じ反復数の探索時間が 2.5 倍以上速い(この PC での計測を記録)。
- 既存のテストが通る。

### リスク
- Worker 間の状態の受け渡し(JSON の構造化複製)のコスト。1回の探索に対して小さい想定だが、計測する。
- UI(ブラウザ)の Worker 数の上限・コア数の取得(`navigator.hardwareConcurrency`)。

## 2. 評価関数・プレイアウトの質の改善(M7-16)

### 目的
探索単体の判断を、ルールベースの手の選び方より強くする。現状は上乗せ 0 で 16%。

### 方針
1. **強さの測定基準を整える**: 測定スクリプトをリポジトリに入れる(CLI から再現できる形)。同じシード・同じ組の対戦で、変更の前後を比べる。誤差(Wilson の区間)を併記する。
2. **評価関数の重みの調整**([eval.ts](../src/ai/eval.ts)): 場・シールド・手札・マナ・コストの重みを、自己対戦で座標降下的に調整する。
3. **プレイアウト方針の質**([mcts.ts](../src/ai/mcts.ts) の `rolloutPick`): 質問(`may` / `block` / 選択)のランダム性を、L1 の評価に近づける。
4. **打ち切りの扱い**: 3ターン先の評価をそのまま使うか、終端に近い局面では実際の勝敗に寄せる。

### 受け入れ条件
- 同じ条件(上記4組・各200試合・反復120)で、変更前より有意に強い(95%区間が重ならない、または +3pt 以上)。
- 上乗せを小さくしても(0.04 など)、L1 に負けない。
- 速度が悪化しない(同じ反復数の時間が +10% 以内)。

### リスク
- 評価関数の過学習(2デッキだけの最適化)。保留シードで検証する。
- 重みの変更は、ゴールデンテストの固定値を更新する(意図した変更として記録)。

## 3. Rust への一部移行(M7-17、別ブランチ `feat/rust-engine`)

### 目的
エンジンの実行速度を数倍にし、確率調査・パターン調査・大量バッチの試行数を増やす。

### 方針
- **別ブランチ**で作業する(リスクが高いため。`main` には、効果が実測で確認できてから取り込む)。
- Rust → WASM(ブラウザ・Worker)と、同じコードのネイティブ版(CLI)。
- 最初の範囲は「プレイアウトに必要な範囲」: 状態・合法手・`step`・カード効果の VM のうち、現行のカードプールで使うもの。AST(`cards.json`)は `serde` でそのまま読む。
- JS と WASM の境界をまたぐ回数を減らす: 「プレイアウトを最後まで」「1試合まるごと」を Rust 側で完結させ、結果だけ返す。
- **TS 版を基準(オラクル)として残す**: 同じシード・同じデッキ・同じ行動列で、Rust 版と TS 版の状態の hash が一致することを検査する(差分テスト)。

### 受け入れ条件(段階)
1. 環境: Rust ツールチェーンが入り、`cargo test` が通る。
2. 状態と `legalActions` が TS 版と一致する(差分テスト)。
3. ランダム同士の試合が、全手順で TS 版と一致する。
4. 速度の測定: プレイアウト/秒が TS 版の何倍か。**5 倍に満たなければ、そこで止めて判断する**。
5. WASM としてブラウザの Worker から呼べる。

### リスク
- カード効果の VM(誘発・置換・再開可能な実行)の移植量が多い。取りこぼしがルールのバグになる。
- ルールの不明点台帳(L1〜)の扱いを、2つの実装で揃える必要がある。
- ビルド環境(Rust ツールチェーン、`wasm-bindgen`)の導入が必要。

## 4. 進め方

1 → 2 → 3 の順。各項目は、1つの目的ごとにコミットする(CLAUDE.md の方針)。測定は、同じ条件で前後を比べ、数値を ROADMAP とコミットメッセージに残す。
