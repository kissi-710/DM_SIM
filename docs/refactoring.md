# リファクタリング計画と記録

目的: **動作を変えずに**、保守性と処理速度を上げる。機能を継ぎ足して育ったプロジェクトなので、不合理な処理・重複・巨大な単位が残っていないかを点検し、直す。
流れ(各回とも同じ): ① 方針・注意点の文書化 → ② 問題点の洗い出し(対象の一覧) → ③ 実装 → ④ 動作不変の確認 → ⑤ ドキュメント更新。
これを 2 回行う。2 回目の対象は、1 回目の変更を含むプロジェクト全体。

- 関連: 進捗は [ROADMAP.md](../ROADMAP.md)、作業ルールは [CLAUDE.md](../CLAUDE.md)、未解決の問題は [ISSUES.md](../ISSUES.md)。

---

## 1. 方針(2 回共通)

1. **ルール・カード効果・AI の判断を変えない。** 変えてよいのは「同じ結果を、より少ない仕事で出す」ことと、「同じ働きを、読みやすい形に直す」ことだけ。
2. 速度の向上は、結果(勝敗・手順・乱数の消費)を変えない範囲で行う。**乱数を引く回数・順序は絶対に変えない**(1 回でもずれると、以降の対局がすべて変わる)。
3. 評価順を入れ替える最適化は、**純粋な(状態を書き換えない)判定どうしに限る**。`emit` / `nextId` / `rngNext` / `ask` を含む処理の順序は動かさない(`seq` が変わる)。
4. 1 コミット = 1 つの目的。リファクタと機能変更を混ぜない。挙動を変える変更が必要になったら、リファクタを止めて ISSUES.md に書く。
5. Rust 版(`rust/`)は TS 版が基準。TS の内部の整理は Rust に反映しない(外から見える挙動が同じため)。Rust 版は挙動の差分テスト(`npm run test:rust`)で TS 版と一致し続けることを確かめる。
6. 公開 API(他ファイル・テスト・Worker から使われる名前)は、移動しても元の場所から再エクスポートして、呼び出し側を壊さない。

## 2. 注意点(落とし穴)

| 注意 | 理由 |
|---|---|
| `seq`(イベント ID)の発番順 | `emit` / `nextId` の呼び出し回数と順序がイベント列・因果(`causedBy`)を決める。判定の順序換えで、呼ばれる回数が変わらないようにする |
| `ask` は状態変更の前 | 再開可能な実行(effects 6.5)の規約。整理で順序が入れ替わると「二重に変更される」不具合になる |
| `derive` の関数は純粋 | キャッシュ・早期 return を足してよいが、`Ctx` 以外の隠れた状態を持たせない |
| 配列の順序 | `legalActions` の並びは AI の同点の選び方に効く(先頭の手が選ばれる)。並びを変えない |
| 時間主導(ms)の探索 | 実行時間で結果が変わるので、検証には使えない。反復回数指定の AI だけを検証に使う |
| UI の分割 | テスト(`tests/ui/*`)が import しているパスを壊さない。元のファイルから再エクスポートする |

### 5.3 検討して見送ったもの(理由つき)

| 候補 | 見送った理由 |
|---|---|
| `collect`(誘発の収集)で、`defId` ごとの `uid` の索引を持ち、全カードの走査をやめる | `determinize`(AI の決定化)は、`deckIds` を共有したまま `cards[].defId` を書き換える。`deckIds` などをキーにした索引は、決定化した状態で誤る。状態ごとに索引を作ると走査と同じ費用 |

### 5.4 第 2 回で起きた不具合と、その検出(R2-6)

R2-6 を最初に実装した時、同名の札を **ゾーンを問わず** 最初の 1 枚だけ調べるようにした。結果は次のとおり。

| 確認 | 結果 |
|---|---|
| `npm test`(1205 件)・挙動スナップショット(当時 178 件)・当時の新テスト(約 1900 局面) | **すべて通過**(不具合を検出できなかった) |
| `npm run test:rust`(Rust 版との差分。MCTS の深い局面を含む) | **失敗**: `tree_matches_ts`(木探索の報酬の合計が、TS 版と Rust 版で 0.10 ずれた) |

原因: マナゾーンの同名の札は、**タップ状態が札ごとに違い**、「自分自身を支払いに使えるか」が変わる。ヨビニオン・トライブ(コスト 4・マナゾーンから召喚できる)が、アンタップ 1 枚・タップ済み 1 枚・他のマナ 3 枚で並ぶと、アンタップの 1 枚は(自分以外の 3 枚では払えず)使えず、タップ済みの 1 枚は(アンタップの 1 枚 + 3 枚で払えて)使える。最初の 1 枚だけを調べると、使えるはずの手が落ちる。手札の札には札ごとの状態がなく、同名なら使えるかどうかも同じ。

対応(`dd2c084`): 省略を手札だけにし、この局面を再現するテストを追加した(`tests/engine/play-actions-copies.test.ts`)。あわせて挙動スナップショットを、**毎手の合法手の列の hash と、合法手列挙の広域確認(800 局)**を含む形に強めた(978 件)。ただし、この 800 局でも、元の不具合は検出できなかった(局面が珍しい)。**スナップショットだけでは、まれな局面の変化を保証できない。`npm run test:rust` と `scripts/diff-fuzz.ts` を併用する**ことを、§3 の表に明記した。

### 5.7 今後の指針

- 挙動を変えない変更は、**必ず** スナップショット・`npm run test:rust`・(広く変える時は)`scripts/diff-fuzz.ts` の 3 つで確かめる。1 つだけでは、まれな局面を見逃す(§5.4)。

- `engine/procs.ts` の分割と、`collect` の索引化は、設計(状態を変える前に質問する規約、決定化との関係)から見直す必要がある。やるなら、独立したテスト(合法手・誘発順の差分)を先に厚くしてから。
