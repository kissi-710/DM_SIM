# バッチ対戦の「必要な試合数」と「探索の反復回数の飽和」(2026-10 の調査)

バッチ画面の「参考資料」パネル(`src/ui/BatchGuide.tsx`)の根拠。測定は `scripts/saturation/`、生データは `docs/data/saturation-2026-10/`。

## 1. 勝率を ±1% で言うのに必要な試合数

**結論: 計算で出せる。** 二項分布の式 n = 1.96² · p(1−p) / ε² が、実測とよく合う。

| 真の勝率 p | ±5% | ±3% | ±2% | ±1% | ±0.5% |
|---|---|---|---|---|---|
| 50% | 385 | 1,068 | 2,401 | **9,604** | 38,416 |
| 60/40% | 369 | 1,025 | 2,305 | 9,220 | 36,879 |
| 70/30% | 323 | 897 | 2,017 | 8,068 | 32,270 |
| 80/20% | 246 | 683 | 1,537 | 6,147 | 24,586 |
| 90/10% | 139 | 385 | 865 | 3,458 | 13,830 |
| 95/5% | 73 | 203 | 457 | 1,825 | 7,300 |

実測での確認(ルールベース同士、4デッキの全順列 16 組 × 6,000 試合 × 先攻後攻の方式 3 通り = 28.8 万試合):

- 1 試合の SD は √(p(1−p)) とほぼ一致(例: p=0.20 で 0.40、p=0.29 で 0.455、p=0.5 で 0.500)。
- 重ならない N 試合(N = 100〜1000)のブロック間のばらつき(推定の SD)は、式の値の 1.0〜1.1 倍(設計効果 1.00〜1.09。ブロック数が少ない N=1000 で最大 1.25 だが、SD の推定誤差の範囲)。
- **交互・ランダム・複製対局のどれでも必要試合数は同じ**。複製対局が効くのは、同じデッキ・同じ AI の対戦だけ(ルールベースのミラーは配りが同じなので、ばらつき 0 で常に 50% になる)。デッキが違う組は、席を入れ替えても配りが同一にならず、効果はない。
- 「落ち着く」を「その後ずっと ±1% 以内」と読むと、固定の N より多く要る。経路のシミュレーション(1,500 経路)で、95% の経路が以後ずっと帯に収まる試合数は p=0.5 で 12,770(式の 1.33 倍)、p=0.8 で 7,885(1.28 倍)、p=0.9 で 4,563(1.32 倍)。目安は約 1.3 倍。
- 必要試合数は AI の強さ・反復回数に依らない(勝率だけで決まる)。反復を増やすと 1 試合が遅くなるだけ。

## 2. 探索の反復回数の飽和

測定: 探索 AI(モンテカルロ、反復 N)を (a) ルールベース、(b) 反復 2N の同じ AI と対戦させる。
デッキの組は maruru/maruru・zardy/zardy・maruru/zardy・zardy/maruru の 4 組(デッキの有利不利が相殺される)。
複製対局(同じ配りで席を入れ替え)。ペア単位の分散で 95% 区間を出す。
(b) は N = 5〜640 の各 1,600 試合、(a) は N = 5〜1280 の各 800 試合。

| 反復 N | N が ルールに勝つ率 | 2N が N に勝つ率 | 判定 |
|---|---|---|---|
| 5 | 64.6% ±3.1 | 56.8% ±2.2 | 伸びる |
| 10 | 71.4% ±2.9 | 56.8% ±2.3 | 伸びる |
| 20 | 80.8% ±2.7 | 57.2% ±2.2 | 伸びる |
| 40 | 85.4% ±2.3 | 54.6% ±2.3 | 伸びる |
| 80 | 89.4% ±2.1 | 52.9% ±2.2 | 緩やか |
| 160 | 92.8% ±1.7 | 52.0% ±2.2 | 緩やか |
| 320 | 92.4% ±1.8 | 52.3% ±2.0 | 緩やか |
| 640 | 93.0% ±1.7 | 51.3% ±2.1 | ほぼ飽和 |
| 1280 | 93.3% ±1.7 | (未測定) | |

- **対ルールの勝率は反復 160 で 93% 前後に達し、以後は動かない**(160〜1280 の差は区間内)。ただし 90% 付近は天井で、感度が低い。
- **反復を 2 倍にした時の伸びは、40 まで +5〜7pt、80 で +3pt、160 以降は +1〜2pt**。160・320・640 をまとめると、2N 側の勝率は 52.1%(約 ±1.3)で、0 ではないが小さい(約 +2pt/倍)。
- 実用上の飽和点は **反復 80〜160**。それ以上は、時間が倍になる割に強さは倍ごとに約 2pt しか伸びない(1 試合の時間は 80 で 0.27 秒、160 で 0.43 秒、640 で 1.2 秒、1280 で 2.0 秒。このクラウド環境の 1 コア)。
- 画面の既定(反復 40)は「まだ伸びる」側。対ルールで 85%。
- 限界: 各行の区間は ±2pt 前後で、隣の行との差は誤差の内。160 以降が本当に 0 に収束するか(+2pt のままか)を ±1pt で言うには、各行 1 万試合以上が要る(§1 の式)。また、これは **ルールベースを土台にした今の探索(horizon=3・評価関数)の頭打ち**で、AI を変えれば飽和点も変わる(docs/ai-quality-plan.md)。

## 3. 再現

```
scripts/saturation/run.sh out.jsonl --a mcts:80 --b mcts:160 --pairs maruru/maruru,zardy/zardy,maruru/zardy,zardy/maruru --games 400 --chunk 2
npx tsx scripts/saturation/analyze-precision.ts dup.jsonl alt.jsonl rand.jsonl
npx tsx scripts/saturation/build-table.ts <dir> <ログ> src/ui/data/iterations.json
```

`run.sh` は全コアに shard を並べる(`K=並列数`)。別マシンに分けるなら、`collect.ts --shard i/K` を各マシンで回して JSONL を連結する。
このリポジトリの既存の `--jobs` 並列(worker_threads)は、この環境(Node 22 + tsx)では `ERR_UNSUPPORTED_DIR_IMPORT` で動かないので、子プロセス方式にした。
